## Independent review and remediation

An independent reviewer agent read all five original commits in full, traced
every retention/boundary/atomicity/redaction claim against the literal code
(not the commit messages), and ran both verification suites itself. Verdict:
no P1s; both gates green. Two P2 gaps identified and fixed prior to marking
this milestone DONE:

1. **Untested cross-module visibility dependency** — `AnalyticsService`,
   `HistoryService`, and `StudentService.get_exam_result` read through `Exam`,
   which is now subject to DATA-003's default soft-delete exclusion. Their
   safety rests entirely on `exam_service.delete_exam`/`topic_service.
   delete_topic`/`question_service`'s pre-existing retained-record guards
   (which block soft-deleting any Exam/Topic/Question that still has
   Submissions) — an invariant that was true but neither documented nor
   tested from the reader side. Fixed in `50390ef`: added cross-referencing
   comments at all three guard sites and at `soft_delete.py`'s module
   docstring, plus a new positive-visibility integration test proving
   Analytics/History/StudentService still see submission/grade data for a
   live exam/topic/question with a submission.
2. **Missing persistent purge-job ledger** — the approved change contract
   requires "a recoverable job/receipt for deterministic retry" so a crash
   between the purge transaction's commit and the physical file's finalize
   step doesn't orphan the quarantined file forever. Fixed in `43409e9`: the
   new `purge_jobs` ledger (migration `1dfa8dca16d5`) plus
   `reconcile_pending_purge_jobs`, with a test that simulates the exact crash
   window and proves reconciliation recovers the file.

## Impact

- API/event/schema contract: Additive only — `POST .../restore` for the five
  governed roots. No existing response shape changed. OpenAPI snapshot grew
  from 51 to 56 paths, reviewed at each step.
- Migration/data: Two new heads, both additive: `f9f952e6df1a` (soft-delete
  columns) and `1dfa8dca16d5` (purge-job ledger). Neither backfills or
  mutates existing data. Both downgrades are guarded against silent data loss.
- Security/ownership/tenant: Restore is owner-teacher-or-admin only, enforced
  through the existing `evaluate_owned_resource` policy layer. Purge is
  admin-only. Every restore/purge/audited mutation commits its audit row in
  the same transaction as the business change (flush-then-single-commit,
  rollback-on-exception) — no path produces a false-success audit gap.
- Retention policy: Submissions, grades, and `audit_events` are structurally
  unreachable from any purge code path (hardcoded to a single `StudyMaterial`
  delete statement plus read-only checks against `Question`/`FlashcardDeck`/
  `TopicBrief`, no generic/parameterized entity dispatch). User, Exam,
  Question, and Topic purge remains blocked in this MVP, per the approved
  policy in `CANONICAL_PROJECT_SPEC.md` §6.3.
- Dependency/toolchain: No new dependency.

## Rollback

- Code: revert the relevant commit(s); the additive soft-delete/purge-job
  columns and tables may remain in place safely (they are additive and
  unused if the application code reverts).
- Data: do not downgrade a shared/live database as an application rollback
  mechanism. The soft-delete-column downgrade refuses while any row has
  `deleted_at` set; the purge-job-ledger downgrade is a plain additive-table
  drop and only safe on a disposable/test database.
- Purge: disable/stop invoking `purge_soft_deleted.py apply` first; inspect
  any `pending_finalize` `purge_jobs` rows via `reconcile` before any code
  rollback — never reclassify a pending row as complete without storage
  evidence.
